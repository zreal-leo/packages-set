# Releasing packages

This repository uses Changesets to keep `branch-create`, `console-temp`, and `fmt-init` independently versioned. Contributors record release intent in feature pull requests; GitHub Actions maintains a Version Packages pull request and publishes only after that pull request is merged.

## Contributor workflow

1. Make and validate the package change:

    ```sh
    pnpm run check
    ```

2. Add release metadata:

    ```sh
    pnpm changeset
    ```

3. Select every affected package, choose the semantic version bump, and write a user-facing summary.
4. Commit the generated `.changeset/*.md` file with the implementation.

A changeset is normally unnecessary for documentation-only changes, CI configuration, tests, repository maintenance, or changes that do not affect a published package.

The Changesets Status workflow comments on pull requests to make missing or unexpected release metadata visible. It does not execute pull request code.

## Version Packages pull request

After a pull request containing changesets is merged into `main`, the Release workflow creates or updates one pull request titled `chore: version packages`.

Review that pull request for:

- the expected packages and semantic version bumps;
- accurate `CHANGELOG.md` entries;
- consumed changeset files;
- unchanged versions for unaffected packages.

Do not run `changeset version` locally for normal releases. Merging the Version Packages pull request is the approval to publish.

The Version Packages pull request is created with the repository `GITHUB_TOKEN`. GitHub creates its pull request workflow runs in an approval-required state to prevent recursive automation. A maintainer with write access must select **Approve workflows to run** after the bot creates or updates the pull request. This keeps the workflow token short-lived and avoids maintaining a separate GitHub App private key. The merged `main` commit is always checked again before the publish job can run.

## External configuration

### npm Trusted Publishers

Configure all three npm packages with the following GitHub Actions Trusted Publisher:

- Organization or user: `zreal-leo`
- Repository: `packages-set`
- Workflow filename: `publish.yml`
- Environment: `npm`
- Allowed action: `npm publish`

Packages:

- `branch-create`
- `console-temp`
- `fmt-init`

Trusted Publishing requires a GitHub-hosted runner, `id-token: write`, Node.js 22.14.0 or newer, and npm 11.5.1 or newer. The workflow satisfies these runtime requirements and does not use `NPM_TOKEN`.

After a successful migration, set each package's publishing access to require two-factor authentication and disallow traditional tokens.

### GitHub Environment

Create an environment named `npm` and configure:

- deployment branches restricted to `main`;
- required maintainer approval if every release should have a final manual gate;
- no npm token secrets.

The environment name must exactly match the npm Trusted Publisher configuration.

## Automated release sequence

1. Validate the `main` commit with type checking, lint, and all package builds.
2. Create or update the Version Packages pull request when pending changesets exist.
3. Compare local package versions with the npm registry.
4. Enter the protected `npm` environment only when a local version is unpublished.
5. Repeat all checks in the publish job.
6. Publish with npm Trusted Publishing.
7. Push the package tags generated by Changesets.
8. Create a GitHub Release for each new package tag.

The non-cancelling release concurrency group prevents overlapping publication attempts.

## Failure recovery

### Validation failure

Fix the failure in a normal pull request. No package is published before all checks pass.

### Trusted Publishing authentication failure

Verify the npm Trusted Publisher values, including the exact workflow filename and environment name. npm does not validate these values when they are saved.

### Partial publication

The workflow lets `changeset publish` finish with a recorded failure, then pushes tags and creates GitHub Releases for packages that succeeded before reporting the job failure. Rerun the failed Release workflow: Changesets checks npm first, skips versions already present, and publishes the remaining versions.

### Missing GitHub Release

Rerun the release creation command for the existing package tag:

```sh
gh release create '<package>@<version>' --verify-tag --title '<package>@<version>' --generate-notes
```

## One-time historical tag reconciliation

The npm registry contains releases newer than the current remote tags. Review the listed commits, then create and push the missing annotated tags once:

```sh
git tag -a branch-create@1.0.12 3e7a4cb -m 'branch-create@1.0.12'
git tag -a branch-create@1.0.13 d7466d4 -m 'branch-create@1.0.13'
git tag -a console-temp@1.0.7 d7466d4 -m 'console-temp@1.0.7'
git tag -a fmt-init@1.0.12 d7466d4 -m 'fmt-init@1.0.12'
git tag -a branch-create@1.0.14 43c3982 -m 'branch-create@1.0.14'
git tag -a console-temp@1.0.8 43c3982 -m 'console-temp@1.0.8'
git tag -a fmt-init@1.0.13 43c3982 -m 'fmt-init@1.0.13'
git push origin \
    branch-create@1.0.12 \
    branch-create@1.0.13 \
    console-temp@1.0.7 \
    fmt-init@1.0.12 \
    branch-create@1.0.14 \
    console-temp@1.0.8 \
    fmt-init@1.0.13
```

These commands are intentionally not part of the automated migration. Confirm every commit-to-version mapping before running them.
